# 插件改进分析：让"任务↔网络匹配"的判断更完整

> 依据：项目自身的框架文档（`framework.md`、`output-mapping-discreteness.md`）与
> 2026-09-30 战役（PA1 阶梯与 CP-H 双轴；判定见同目录
> `cifar10-anchor.md`）。
> 本文回答：读完这些文档之后，**项目（Capacity Lens）要具备"判断任务与网络是否匹配"的能力，还差什么、该怎么补**。
> 核心立场先行：匹配判断的**否定半已在真实任务上验证**；改进的方向不是"让它能预测更多"，
> 而是**把否定半做全、把布线词汇补齐、把适用域预检做进工具**。

---

## 0. 总判断

A-001 把网络钉死为"输入→输出的映射、其性质只定义在输出边界"；A-002 把架构演进钉死为
"大映射 → 路由 × 局部函数"。这两条立场对匹配判断的含义是结构性的：

1. **能匹配吗（否定半）** —— 由输出边界的通过量（Fano/DPI）决定，**已可证、且已在真实任务上验证**（CP-H R1a/R1b 3/3）；
2. **配得好不好（肯定半）** —— A-001 明说"合适永远相对于任务"，而输出坐标系由任务定义 ⇒ **没有跨任务标尺，理论上就不该做**；
3. **配得顺不顺（代价半）** —— A-002 的主战场（可达性 / 干扰 / 兑换率），**只在任务内可排序**（opt_demo 已实现）。

所以"改进项目，使其能匹配任务与网络结构"的正确读法是：**把 1 做全、把 3 的任务内版本做顺、把 2 的边界显式写进产品**。以下五条具体启发，按"理论依据 → 现状缺口 → 改动候选"组织。

---

## 1. A-002 的最大启发：容量判断升级为"存储层 + 流层"两层

**理论依据**：A-002 §5.3 的修正 —— 路由不创造信息，但它改变"容量—计算—存储"的兑换率；
**MoE 总参数的增加是真实的容量增加**（同激活预算下更优，同总参数下通常不优）。§4.5 的双侧分解：
注意力分解**记忆访问**、MoE 分解**参数激活**。

**现状缺口**：项目的容量拓扑规则只有两条 —— 纯串联取 `min`、有旁路取 `sum`（P4）。这是为
**前馈瓶颈链**设计的单层规则，没有"路由 × 局部函数"的词汇。拿它去判一个 MoE/Transformer，
会系统性答错：

- MoE 的总容量是**所有专家参数之和**（存储层，可加），而单样本的通过量是**被激活的
  top-k 专家路径上的最窄处**（流层，取 min）；
- 注意力层的 KV 是**内容可寻址的存储器**（A-002 §3.2）：上下文长度 × 每 token 的信息是它的
  存储容量，单次读出的信息量是它的流层容量；
- 现有 `min_capacity_serial` / `sum_capacity_parallel` 恰好是这两层的退化情形：纯串联 = 只问流层，
  纯并联 = 只问存储层。

**改动候选**（中成本，纯增量、不破坏现有 API）：

1. `capacity.py` 增加 **wiring-aware 两层容量界**：
   - `storage_capacity(wiring)`：总参数 / 总码本项数的口径（对分支/专家取 sum）—— 回答"映射到底存不存得下"；
   - `flow_capacity(wiring, activated)`：激活路径的口径（沿激活路径取 min）—— 回答"单个样本能不能把任务信息流过去"；
   - 布线图用一个轻量描述表达（节点 = 层、边 = 路径、路由 = 条件激活），`min`/`sum` 退化为特例。
2. README 增加一张"现代架构布线判定表"（dense 串联 / 残差 / 注意力 / MoE —— 各自用哪一层判、判什么）。
3. 匹配判断的供给面应把两层都报出来：**"存储容量够但流层不够"（MoE 激活太少）与"流层够但存储不够"
   是两种不同的不匹配，排除理由也不同** —— 这正是产品化价值。

## 2. A-001 的启发：架构即布线 ⇒ 匹配判断的前置步骤是"布线图判读"

**理论依据**：A-001 第 V 节实践姿态 #4 —— "架构即布线：设计网络 = 选择输入信号走哪些路径、以及在抵达
输出空间的路上被如何重新编码"；#1 —— "一切测量都取在输出边界"。

**现状缺口**：项目的拓扑判断只有 P4 的 min/sum 二选一，而且要求用户**自己先判拓扑**（用错会严重
低估；0.103→0.876 的教训）。工具没有把"布线判读"做成结构化的前置步骤。

**改动候选**（低成本，流程级）：

把匹配判断固化为**五步判据包**，其中每一步要么已经存在、要么是一个可实现的增量：

| 步 | 内容 | 现状 |
| --- | --- | --- |
| 1 判布线 | 读网络结构 → 确定容量公式（两层口径，见 §1） | 只有 min/sum 二选一，缺现代词汇 |
| 2 测任务需求 | H(Y) 硬上界 + R_IB（Fano，来自参照模型）→ **K_min 量子化** | 已有（CP-H 验证了量子化） |
| 3 测网络供给 | 按布线公式算存储/流容量 | 缺两层口径 |
| 4 判排除 | 供给 < 需求 ⇒ 确定装不下（可证、方向安全） | 已有，真实任务 3/3 成立 |
| 5 代价排序 | 排除不成立时，只给一个**任务内**的归一化代价排序 | 已有（opt_demo）；边界必须写清 |

这五步就是"任务↔网络匹配判断"的完整形态 —— **全部落在理论允许的范围内**（否定 + 任务内排序），
不越界去承诺肯定半。

## 3. CP-H / P-A1-4 的启发：墙几何预检 —— 主动告诉用户"哪一半适用"

**理论依据**：战役产出的新命题 P-A1-4 —— **悬崖锐度是输出映射离散度的函数，不是容量的属性**。
grid64：输出完全可分（err_1nn=0）→ 映射离散 → K<64 时一步装不下 → 悬崖；CIFAR-10：输出弥散
（err_1nn=0.23）→ 映射弥散 → Fano 排除仍成立（第一步），但在那个 K 之上是逐级逼近、没有悬崖。
**排除依赖 (a) 信息量，定位依赖 (b) 离散度 —— 两者长期被混同为"任务有墙"这一个前提。**

**现状缺口**：工具把"K* 定位"当作默认功能给出，而用户只有在真实任务跑完之后才撞见"平台未建立、K* 不可定位"
（CP-H 的体验）。工具不会**事先**告诉用户这个任务上哪一半适用。

**改动候选**（低成本，零训练，沿用 cpe/cpf 探针先例）：

1. 新增一个**墙几何探针**：读参照模型的特征 → err_1nn / silhouette / ceiling（已有的现成函数）→ 把任务分类为
   - **离散墙**：err_1nn≈0 → K* 定位适用（合成硬墙类任务）；
   - **弥散墙**：err_1nn ≫ 0 → 只承诺排除（K_min + 可证筛除），并显式输出"本任务不承诺 K* 定位"。
2. 产品行为：预检结果打印在判定报告的开头 —— **"这个任务我能给你 K_min 和排除，但别指望我定位 K*"**，
   把 CP-H 的教训变成工具的默认话术，而不是用户自己的踩坑经历。
3. 附带：这把 P-A1-4 直接从"台账候选预测"变成"插件功能"；跑完 δ 剂量响应之后，探针阈值就可以标定。

## 4. E-001 方法论教训的启发：判定前置检查清单（gate/plateau ≈ router 纯度）

**理论依据**：索引条目 E-001 的教训 —— "凡路由/划分类实验，必须先验证 router 纯度这个中间量，再看性能结论。
v1 没验纯度，于是测的是训练配方而不是假设。"**一个结论所依赖的中间量必须先自检**；这是索引体系里最值钱的一条纪律。

**现状缺口**：项目的中间量自检散落在实验脚本内部（G0 双门、码本利用率、平台前置条件、量子化门槛），
但没有作为**判定输出的一部分**暴露出来。用户拿到一个 K_min 数字，却不知道它背后的哪些中间量已经自检过。

**改动候选**（低成本，API 级）：

1. 判定结果附带一份**前置检查清单**，逐项二值化：
   - teacher 已编码任务？（acc 门）
   - 码本未塌缩？（H(Z_t) ≥ 0.8·ln K_t）
   - 平台已建立？（落差曲线的顶端已收敛）
   - 门槛在量子化区间内？（K_min 体制，CP-H 标定法）
   任何一项不过 → 判定自动降级为 "RESTRICTED/UNDECIDABLE"；绝不静默给出一个数字。
2. 运行环境披露：±0.03 的 CUDA 运行间方差（CP-H 实测）作为报告里的固定一行 —— 把读数口径纪律产品化。

## 5. 文档为自己划定的禁区（改进时绝不能做的事；列出来是为了不越界）

1. **不要预测"哪个架构更好"（跨任务）** —— A-001：输出坐标系由任务定义；A-002 §5.3：架构差异是 axis-3 的内容。工具的架构语句只允许说"在该任务下是否可行 / 任务内的代价排序"。
2. **不要把内部读数当质量指标** —— P-A1-1 的弱形式已经做过对照：非空但冗余，全部不敌 H(Z)/acc。一个新指标在上马之前必须先过最廉价的仲裁。
3. **不要承诺充分性** —— "装得下 ⇒ 会好"永远不成立；A-001 §3.3 的守恒律只有证否方向。
4. **MoE 容量口径**：总参数算容量（A-002 §5.3 的修正）；绝不能只看激活路径 —— 否则"存储换计算"会被读成"没有容量增长"。
